# ADR-012: Testing Strategy

## Status

Accepted

## Date

2024-05-01

## Context

A healthcare platform that handles PHI requires a high confidence level in correctness and regression prevention. The testing strategy must:

- Catch regressions before they reach production
- Cover the API contract so third-party integrations do not break silently
- Verify HIPAA-relevant security behaviours (security headers, auth flows, data encryption)
- Provide performance baselines so regressions in throughput are detected
- Be fast enough to run in CI without blocking developers

## Decision

A multi-layer testing pyramid is adopted:

### Layer 1 — Unit and Integration Tests (Jest + Supertest)

**Framework**: Jest 30 + Supertest  
**Scope**: API service (`apps/api`)  
**DB isolation**: `mongodb-memory-server` — a real in-memory MongoDB instance per test suite, no mocking of the ODM layer  
**Coverage targets**:

| Metric | API target | Web target |
|--------|-----------|-----------|
| Line coverage | 80 % | 70 % |
| Branch coverage | 75 % | 65 % |

Coverage is uploaded to Codecov on every CI run. Falling below targets fails the CI pipeline.

Security-specific tests run in their own pass (`--runInBand src/__tests__/security-headers.test.ts`) to verify Helmet, CORS, and CSRF headers are present on every response.

### Layer 2 — End-to-End Tests (Playwright)

**Framework**: Playwright 1.44  
**Scope**: Web application + API stack running as Docker images  
**Modes**:

- **Functional E2E**: user-journey tests (login, patient registration, encounter creation, payment)
- **Visual regression**: screenshot comparison using Playwright's built-in comparison; screenshots stored as CI artifacts
- **Accessibility**: `@axe-core/playwright` integration; WCAG 2.1 AA violations fail the suite

E2E tests run in Stage 5 of CI against the built Docker images, ensuring the tested artefact is identical to what gets deployed.

### Layer 3 — Contract Tests (Pact)

**Framework**: Pact 14 (consumer-driven contract testing)  
**Scope**: API service ↔ web/mobile consumers  

Consumer-driven contracts are generated by the web/mobile client tests and verified against the API. This ensures the API never introduces a breaking change for a known consumer without the contract being updated. Contract tests run in a separate CI workflow (`contract-tests.yml`).

### Layer 4 — Mutation Tests (Stryker)

**Framework**: Stryker 8.7  
**Scope**: API business logic  
**Purpose**: Verify that unit tests are effective — a test suite with high line coverage but weak assertions is caught by mutation testing.

Stryker introduces deliberate code mutations (e.g. flipping `>` to `>=`, changing return values) and checks whether the test suite detects them. Mutation score targets are tracked in `apps/api/docs/mutation-score-tracking.md`. Mutation tests run on a separate schedule (not every commit) due to runtime cost.

### Layer 5 — Performance Tests (k6)

**Framework**: k6  
**Scope**: Key API endpoints (patient list, authentication, encounter creation)  
**CI trigger**: Separate `performance.yml` workflow, triggered weekly and on `main` merges  

Performance baselines:
- p95 response time < 500 ms under expected load
- 0 % error rate at 100 concurrent users
- Throughput > 500 req/s on patient list endpoint with warm cache

### Test configuration files

| File | Purpose |
|------|---------|
| `apps/api/jest.config.ts` | Unit + integration tests |
| `apps/api/jest.contract.config.ts` | Pact contract tests |
| `apps/api/jest.mutation.config.cjs` | Stryker mutation runner config |

## Consequences

### Positive

- `mongodb-memory-server` provides full ODM fidelity without a running MongoDB cluster in CI.
- Contract tests catch API breaking changes that unit tests miss (they test the actual HTTP contract).
- Mutation tests surface weak assertions — a common failure mode when teams optimise for line coverage alone.
- Visual regression tests catch unintended UI changes in clinical workflows.
- Axe accessibility tests ensure the portal is usable by clinical staff with disabilities.

### Negative / Trade-offs

- `mongodb-memory-server` is slower than pure in-memory mocking (~200 ms startup per suite); running suites in parallel mitigates this.
- Stryker mutation tests can take 10–30 min for large codebases; they are not run on every commit.
- Maintaining Pact contracts adds overhead when the API contract evolves; contract files must be updated before the API change can merge.
- Performance tests require a realistic data set to be meaningful; a small test DB gives misleading results.

### Neutral

- The `--run` flag is used for single-execution test runs in CI (rather than watch mode) to prevent hanging processes.

## Alternatives Considered

| Option | Why Rejected |
|--------|-------------|
| Pure mocking of MongoDB (jest.mock) | Misses ODM validation, index behaviour, and middleware hooks that are critical to correctness |
| Cypress instead of Playwright | Playwright has better multi-browser support, headless performance, and native accessibility tooling |
| Only unit tests | Insufficient for a healthcare API where integration behaviour (middleware ordering, DB constraints) is as important as business logic |
