## Login Flow Overview

Understanding the full flow prevents most auth issues:

```
Standard login (no MFA):
  POST /auth/login
    → validate email + password
    → check account not locked
    → check MFA grace period
    → return { accessToken, refreshToken }

Login with MFA enabled:
  POST /auth/login
    → validate email + password
    → return { status: "mfa_required", tempToken }
  POST /auth/mfa/challenge
    → validate tempToken (5-min expiry)
    → validate TOTP code
    → return { accessToken, refreshToken }

Login with MFA using backup code:
  POST /auth/mfa/backup
    → validate tempToken
    → validate backup code (single-use)
    → return { accessToken, refreshToken, remainingBackupCodes }

Token refresh:
  POST /auth/refresh
    → validate refreshToken (7-day expiry)
    → detect replay → revoke family if reused
    → return { accessToken, refreshToken } (rotated)

Logout:
  POST /auth/logout
    → delete refreshToken from DB
    → add accessToken jti to Redis denylist
```

## JWT Errors

### `MISSING_ISSUER` / `INVALID_ISSUER`

The token's `iss` claim does not match `JWT_ISSUER` (`health-watchers-api` by default).

**Diagnosis:**
```bash
# Decode the token (base64 middle segment)
node -e "
const token = 'YOUR_TOKEN';
const payload = JSON.parse(Buffer.from(token.split('.')[1], 'base64').toString());
console.log('iss:', payload.iss);
console.log('aud:', payload.aud);
console.log('exp:', new Date(payload.exp * 1000).toISOString());
console.log('jti:', payload.jti);
"

echo "Server expects iss: $JWT_ISSUER"
```

**Fix:** Ensure `JWT_ISSUER` is identical across all services that issue and verify tokens. Never change it without rotating all tokens.

---

### `MISSING_AUDIENCE` / `INVALID_AUDIENCE`

The token's `aud` claim does not match `JWT_AUDIENCE` (`health-watchers-client` by default).

**Fix:** Same as issuer — keep `JWT_AUDIENCE` consistent. Check `config.service.ts` to confirm the value in use.

---

### `TOKEN_EXPIRED` / `MISSING_EXPIRY`

Access tokens expire after **15 minutes** (`JWT_ACCESS_TOKEN_EXPIRY`, default `15m`).

**Client-side fix:** Implement proactive refresh — call `POST /auth/refresh` before the access token expires, not after it fails.

**Recommended pattern:**
```typescript
// Refresh when token has < 2 minutes remaining
const payload = jwtDecode(accessToken);
const expiresIn = payload.exp * 1000 - Date.now();
if (expiresIn < 2 * 60 * 1000) {
  await refreshTokens();
}
```

**Server clock drift fix:** If tokens expire immediately after issuance:
```bash
# Check server time
date -u
# Sync if needed
ntpdate -u pool.ntp.org
```

---

### `INVALID_SIGNATURE` / `MALFORMED_TOKEN`

The token's cryptographic signature is invalid, or the token is not a valid JWT.

**Causes:**
- Token was modified after signing
- Wrong `JWT_ACCESS_TOKEN_SECRET` in use
- Token was copied with extra whitespace or line breaks

**Fix:**
1. Re-authenticate to get a fresh token.
2. Verify `JWT_ACCESS_TOKEN_SECRET` has not changed since the token was issued.
3. Trim the token before use: `token.trim()`.

---

### `MISSING_JTI`

The token does not contain a `jti` (JWT ID) claim, which is required for denylist checks.

**Cause:** Token was generated by an older version of the API that did not include `jti`, or generated by an external system.

**Fix:** Re-authenticate. All tokens generated by `signAccessToken()` in `token.service.ts` include `jti`.

---

### `Token has been revoked`

The `jti` is in the Redis denylist.

**Happens after:**
- Explicit `POST /auth/logout`
- Admin calls `POST /auth/logout-all` for the user
- Security incident token revocation

**Fix:** Re-authenticate. Do not retry with the same token.

---

### `Token has been invalidated — please log in again`

The token was issued before the user's `invalidatedAt` timestamp in Redis. This is set when:
- User calls `POST /auth/logout-all`
- Admin resets all user sessions

**Check Redis:**
```bash
redis-cli -u "$REDIS_URL" GET "user:invalidated:<userId>"
# Returns Unix timestamp — tokens with iat < this value are rejected
```

**Fix:** Re-authenticate.

---

### Token reuse detected — all sessions revoked

```json
{ "error": "Unauthorized", "message": "Token reuse detected — all sessions revoked" }
```

A refresh token was presented a second time. The entire token family is deleted as a replay attack countermeasure.

**Legitimate cause:** Client made two simultaneous refresh calls (race condition).

**Fix:**
1. Add a mutex/semaphore in the client to prevent concurrent refresh calls.
2. Re-authenticate after family revocation.

**Suspicious cause:** If the user did not trigger this, the refresh token may have been stolen. Investigate access logs for the `userId` using the compromised family.

## MFA Issues

### TOTP code always rejected

**Step 1 — Check device clock:**
TOTP is time-based. A clock offset > 30 seconds invalidates the code.

```bash
# iOS/Android: Settings → General → Date & Time → Set Automatically: ON
# Check offset:
ntpdate -q pool.ntp.org
```

**Step 2 — Try the next window:**
Each code is valid for 30 seconds. Wait for the next code if you are near a boundary.

**Step 3 — Verify the secret matches:**
The TOTP secret is stored encrypted in MongoDB. If `FIELD_ENCRYPTION_KEY` changed, decryption fails silently and `verify()` always returns false.

```bash
# Check if FIELD_ENCRYPTION_KEY matches what was used when MFA was set up
grep "FIELD_ENCRYPTION_KEY" /var/log/api/app.log | head -5
# Should show: ✅ set
```

**Step 4 — Re-enroll MFA:**
If nothing else works:
1. Admin resets MFA: `DELETE /api/v1/auth/mfa/disable` (requires password + current TOTP — may need direct DB operation if TOTP is inaccessible)
2. User re-runs setup: `POST /auth/mfa/setup` → scan new QR code → `POST /auth/mfa/verify`

---

### `MFA setup not initiated` on verify

**Symptom:** `POST /auth/mfa/verify` returns `{"error":"Unauthorized","message":"MFA setup not initiated"}`.

**Cause:** `POST /auth/mfa/setup` was not called first, or the `mfaSecret` field on the user was cleared.

**Fix:** Call `POST /auth/mfa/setup` to generate a new secret and QR code, then verify.

---

### Backup code `Invalid or already used`

Backup codes are **single-use**. Once used they are removed from the user's `mfaBackupCodes` array.

**Check remaining codes:**
```bash
curl -H "Authorization: Bearer <accessToken>" \
  http://localhost:4000/api/v1/auth/mfa/backup-codes/count
# Returns: { remaining: N, total: 10, low: true/false }
```

**If no codes remain:** Use TOTP to log in, then regenerate: `POST /auth/mfa/backup-codes/regenerate`.

**If TOTP is also inaccessible:** A SUPER_ADMIN must directly reset the user's MFA in the database:
```javascript
// mongosh
db.users.updateOne(
  { email: "user@example.com" },
  {
    $set: { mfaEnabled: false },
    $unset: { mfaSecret: "", mfaBackupCodes: "" }
  }
)
```
Audit this action manually.

---

### MFA `requiresMfaSetup: true` after grace period expires

**Symptom:** Doctor/Nurse/CLINIC_ADMIN/SUPER_ADMIN gets HTTP 403 on login with `requiresMfaSetup: true`.

**Cause:** The 7-day MFA grace period has elapsed. These roles must have MFA enabled to log in.

**What the response contains:**
```json
{
  "error": "MfaRequired",
  "requiresMfaSetup": true,
  "tempToken": "<5-min token>"
}
```

**Fix:** Use `tempToken` to call `POST /auth/mfa/setup`, scan the QR code, then `POST /auth/mfa/verify`. This completes MFA setup and allows login.

---

### MFA grace period warning on login

```json
{ "warning": "mfa_required", "mfaGracePeriodEndsAt": "2026-09-06T..." }
```

This is an informational warning — login succeeded. Set up MFA before the deadline to avoid being locked out.

---

### Cannot disable MFA for a required role

```json
{ "error": "Forbidden", "message": "2FA is mandatory for your role and cannot be disabled" }
```

Roles `DOCTOR`, `NURSE`, `CLINIC_ADMIN`, `SUPER_ADMIN` have mandatory MFA. This is enforced server-side regardless of the request.

**Fix:** If MFA must be reset (e.g., lost device), a SUPER_ADMIN can reset it directly in the database (see backup code section above), then the user re-enrolls.

---

### Backup codes not received after MFA setup

Backup codes are returned **once** in the `POST /auth/mfa/verify` response and emailed via `sendMfaBackupCodesRegeneratedEmail`. They are never shown again.

**If lost:** Regenerate with `POST /auth/mfa/backup-codes/regenerate` (requires password + TOTP or an existing backup code).

## Account Lockout

### HTTP 423 — Account locked

```json
{
  "error": "AccountLocked",
  "message": "Account is temporarily locked due to too many failed login attempts.",
  "retryAfter": 900
}
```

**Triggers:**
- 5 consecutive failed **password** attempts → `lockedUntil = now + 15 min`
- 5 consecutive failed **MFA** attempts → `lockedUntil = now + 15 min`

**Known issue:** The controller uses `LOCK_DURATION_MS = 15 min` (local constant), while `constants.ts` has `LOCKOUT_DURATION_MS = 30 min`. The effective lockout is **15 minutes**.

**Unlock options:**

1. **Wait** — lockout expires automatically after 15 minutes.

2. **SUPER_ADMIN unlock:**
```bash
curl -X POST \
  -H "Authorization: Bearer <superAdminToken>" \
  -H "Content-Type: application/json" \
  -d '{ "email": "locked-user@clinic.com" }' \
  http://localhost:4000/api/v1/auth/unlock
```

3. **Direct DB unlock (emergency):**
```javascript
db.users.updateOne(
  { email: "locked-user@clinic.com" },
  {
    $set: { failedLoginAttempts: 0, failedMfaAttempts: 0 },
    $unset: { lockedUntil: "" }
  }
)
```

---

### Account locked email not received

The lockout email is sent via `sendAccountLockedEmail()` as fire-and-forget. If SMTP is not configured it fails silently.

**Fix:** Configure SMTP. See [ERR-040](./common-errors.md#err-040--password-reset-email-not-received).

## Session Management

### All sessions suddenly invalidated

**Cause:** `POST /auth/logout-all` was called, or a SUPER_ADMIN triggered a user-level token invalidation.

**Check Redis:**
```bash
redis-cli -u "$REDIS_URL" GET "user:invalidated:<userId>"
# Returns the timestamp when all sessions were invalidated
```

**Fix:** Re-authenticate. If this happened unexpectedly, investigate who triggered `logout-all` via audit logs:
```javascript
db.auditlogs.findOne({
  action: { $in: ["LOGOUT_ALL", "USER_SESSIONS_REVOKED"] },
  "metadata.targetUserId": "<userId>"
})
```

---

### Refresh token missing from database

```json
{ "error": "Unauthorized", "message": "Invalid refresh token" }
```

**Causes:**
- Token was already consumed and rotated (use the new token from the last refresh response)
- Token family was revoked due to replay detection
- Refresh token TTL (7 days) expired — record deleted by MongoDB TTL index

**Fix:** Re-authenticate.

---

### Refresh token rotation fails silently

If `POST /auth/refresh` keeps returning the same access token, the client may be caching the refresh response.

**Fix:** Always store and use the new `refreshToken` returned in every refresh response. The old token is consumed immediately.

## Role-Based Access Control (RBAC)

### Role hierarchy

| Role | Can create | Can access |
|---|---|---|
| `SUPER_ADMIN` | All roles | All clinics |
| `CLINIC_ADMIN` | DOCTOR, NURSE, ASSISTANT, READ_ONLY | Own clinic |
| `DOCTOR` | — | Own clinic |
| `NURSE` | — | Own clinic |
| `ASSISTANT` | — | Own clinic |
| `READ_ONLY` | — | Own clinic (read-only) |
| `PATIENT` | — | Own portal records |

### HTTP 403 — Insufficient permissions

```json
{ "error": "Forbidden", "code": "FORBIDDEN", "message": "Insufficient permissions" }
```

**Diagnose:** Decode the token and check the `role` claim. Verify the route requires a different role.

**Fix:** Use an account with the correct role, or ask a SUPER_ADMIN to grant the appropriate role.

---

### CLINIC_ADMIN trying to create SUPER_ADMIN

```json
{ "error": "Forbidden", "message": "A CLINIC_ADMIN cannot create a SUPER_ADMIN account" }
```

Only `SUPER_ADMIN` can create other `SUPER_ADMIN` accounts. This is enforced by `ROLE_CREATE_PERMISSIONS` in `auth.controller.ts`.

---

### Cross-clinic data access blocked

Tokens are scoped to a `clinicId`. Requests to data from a different clinic return 403.

For SUPER_ADMINs who need to access another clinic: `POST /auth/switch-clinic` with the target `clinicId` to get new tokens scoped to that clinic.

---

### `requireClinicMatch` returning 403

The `requireClinicMatch()` middleware compares the route's clinic parameter against the token's `clinicId`. If they differ (and the user is not SUPER_ADMIN), it returns 403.

**Fix:**
- Ensure the frontend sends requests using the correct clinic context.
- SUPER_ADMINs must use `switch-clinic` to get tokens for the target clinic before accessing its resources.

## Password Reset Issues

### Reset link says `Invalid or expired`

**Cause:** Reset tokens expire after **1 hour**. The token may have already been used.

**Fix:**
1. Request a new link: `POST /auth/forgot-password`.
2. Use the link within 1 hour.
3. Check that the token in the URL is not URL-encoded (the `%` character in the token must not be double-encoded).

---

### `forgot-password` returns 200 but no email arrives

`POST /auth/forgot-password` always returns 200 even if the email doesn't exist (prevents email enumeration). 

**Diagnose:**
```javascript
// Check if a reset token was generated
db.users.findOne(
  { email: "user@example.com" },
  { resetPasswordTokenHash: 1, resetPasswordExpiresAt: 1 }
)
// If resetPasswordTokenHash is set, the token was generated — check SMTP
// If not set, the email is not registered
```

---

### Password reset token used twice

Tokens are not single-use by design — the hash is cleared only after a successful reset. However, `resetPasswordExpiresAt` is checked on every attempt. Once the password is reset, the token fields are cleared.

If the link is clicked twice simultaneously, one request will find no token on the second attempt — this is expected and safe.

---

## Email Verification Issues

### Verification link expired or invalid

Email verification tokens do not have a TTL — they remain valid until used. The "invalid" error means either:

1. The token was already used (user clicked the link twice).
2. The raw token was URL-encoded and the hash doesn't match.
3. The user re-registered, generating a new token that invalidated the old one.

**Fix:** Contact a SUPER_ADMIN to manually verify the email:
```javascript
db.users.updateOne(
  { email: "user@example.com" },
  { $set: { emailVerified: true }, $unset: { emailVerificationTokenHash: "" } }
)
```

## CSRF Issues

### State-changing requests return 403 with no JWT error

**Symptom:** POST/PUT/PATCH/DELETE returns 403 but the JWT is valid.

**Cause:** The CSRF middleware (`csrf.middleware.ts`) rejected the request because `X-CSRF-Token` header is missing or invalid.

**How CSRF tokens work:**
1. The API sets a CSRF cookie on the first request (typically `GET /`).
2. The frontend reads the cookie value.
3. Every mutation must include the value in the `X-CSRF-Token` header.

**Fix:**
```typescript
// Example: read CSRF token from cookie and include in request
const csrfToken = getCookie('csrf-token');
fetch('/api/v2/patients', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${accessToken}`,
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken,
  },
  body: JSON.stringify(data),
});
```

The `X-CSRF-Token` header is included in the CORS `allowedHeaders` list.

## Registration Issues

### `Email already in use` (HTTP 409)

```json
{ "error": "Conflict", "message": "Email already in use" }
```

**Fix:** Use a different email, or recover the existing account via `POST /auth/forgot-password`.

---

### `Clinic with ID '...' does not exist` (HTTP 400)

```json
{ "error": "BadRequest", "message": "Clinic with ID '...' does not exist" }
```

**Fix:** Verify the `clinicId` is a valid MongoDB ObjectId and the clinic exists and is active.

---

### `A CLINIC_ADMIN cannot create a DOCTOR account` in another clinic

**Cause:** Tokens are clinic-scoped. A CLINIC_ADMIN can only create users in their own clinic.

**Fix:** Use a SUPER_ADMIN account to create users in other clinics, or have the target clinic's CLINIC_ADMIN perform the registration.

---

### Verification email not received after registration

The welcome email and verification email are sent asynchronously after user creation. If they don't arrive:

1. Check SMTP configuration.
2. Check API logs for `sendVerificationEmail` errors.
3. Check spam folder.
4. Manually trigger a new verification: contact SUPER_ADMIN.

## Clinic Switching Issues

### `SUPER_ADMIN role required` on `/auth/switch-clinic`

Only SUPER_ADMINs can switch clinics. This endpoint is not available to other roles.

---

### `Clinic not found or inactive`

The target `clinicId` either does not exist or has `isActive: false`.

**Fix:**
```javascript
// Check clinic status
db.clinics.findOne({ _id: ObjectId("...") }, { isActive: 1, name: 1 })
```
If `isActive: false`, reactivate via the clinics management API.

---

### Audit log for clinic switch

Every clinic switch is recorded:
```javascript
db.auditlogs.findOne({
  action: "CLINIC_SWITCH",
  userId: "<userId>"
})
// metadata: { from: "<oldClinicId>", to: "<newClinicId>" }
```

## Security Hardening Reference

### JWT secret strength requirements

| Secret | Minimum length | Generation command |
|---|---|---|
| `JWT_ACCESS_TOKEN_SECRET` | 32 chars | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `JWT_REFRESH_TOKEN_SECRET` | 32 chars | Same as above |
| `JWT_TEMP_TOKEN_SECRET` | 32 chars | Same as above — **not validated by Zod, set manually** |

### Token expiry windows

| Token | Expiry | Config var |
|---|---|---|
| Access token | 15 minutes | `JWT_ACCESS_TOKEN_EXPIRY` |
| Refresh token | 7 days | `JWT_REFRESH_TOKEN_EXPIRY` |
| Temp (MFA) token | 5 minutes | Hardcoded in `token.service.ts` |
| Password reset token | 1 hour | Hardcoded in `auth.controller.ts` |
| MFA grace period | 7 days | `MFA_GRACE_PERIOD_MS` in `auth.controller.ts` |
| Account lockout | 15 minutes | `LOCK_DURATION_MS` in `auth.controller.ts` |

### Auth rate limits

| Endpoint | Limit | Window | Key |
|---|---|---|---|
| `POST /auth/login` | 5 requests | 15 min | per IP |
| `POST /auth/forgot-password` | 3 requests | 1 hour | per IP |
| All other API routes | 300 requests | 15 min | per IP |

### Audit events to monitor

| Action | When triggered |
|---|---|
| `LOGIN_SUCCESS` | Successful login or MFA enable/disable |
| `ACCOUNT_LOCKED` | Account locked after failed attempts |
| `ACCOUNT_UNLOCKED` | SUPER_ADMIN manually unlocked |
| `CLINIC_SWITCH` | SUPER_ADMIN switched to another clinic |
| `MFA_BACKUP_CODES_REGENERATED` | Backup codes regenerated |
